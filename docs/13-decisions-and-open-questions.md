## 대안 검토 메모

- **하단 탭바 vs 선형 단계형 내비게이션**: 짧고 목표지향적인 흐름 특성상 선형 진행을 채택했으나, 사용성 테스트 전까지는 가설이다([02-information-architecture.md](02-information-architecture.md#모바일-내비게이션)).
- **세션 토큰/공유 토큰 인증 방식**: 쿠키 기반 대신 `Authorization: Bearer` 헤더 방식을 채택해 CSRF 위험을 구조적으로 낮췄다([07-api-specification.md](07-api-specification.md), [12-privacy-security-compliance.md](12-privacy-security-compliance.md)).

## 위험

- 명리학/오행 계산의 정확도가 낮으면 서비스 신뢰도에 직접적 타격을 준다 → 사용자 승인 하에 "단순화된 초안"으로 Phase 2를 구현했으며, 프로덕션 공개 전 명리학 자문 검수를 강력히 권장한다([08-recommendation-engine.md](08-recommendation-engine.md), [11-implementation-roadmap.md](11-implementation-roadmap.md#실제-구현-참고-phase-2-오행분석-공유) 참조).
- envelope encryption의 KEK가 환경변수(로컬 `.env.local`)에만 존재하며 실제 KMS로 이전되지 않았다 → 프로덕션 배포 전 반드시 KMS 연동으로 전환해야 한다.
- 위기 표현 감지 정확도가 낮으면(과소 감지) 사용자 안전에, (과다 감지) 사용자 경험에 각각 악영향을 준다 → fail-safe(과다 감지 방향으로 보수적 설계) 원칙을 유지한다([09-ai-prompts-and-safety.md](09-ai-prompts-and-safety.md)).
- LLM 국외 이전 관련 법적 요건 미검토 시 컴플라이언스 리스크가 있다 → Phase 1 LLM 연동 전 법무 검토를 선행 권장한다.
- ~~비회원 세션의 민감정보(생년월일시) 삭제 경로 부재~~ → `DELETE /sessions/current`와 만료 세션 정리(즉시 정리 + 배치 스크립트)로 해결했다([07-api-specification.md](07-api-specification.md#delete-sessionscurrent), [11-implementation-roadmap.md](11-implementation-roadmap.md#실제-구현-참고-phase-2-삭제-경로) 참조). 남은 위험은 배치 스크립트를 실제 스케줄러에 연결하는 인프라 작업뿐이다.

## ADR 후보

다음 항목들은 정식 ADR(Architecture Decision Record)로 문서화할 가치가 있는 결정으로, 실제 구현 착수 시점에 별도 ADR 작성을 권장한다.

1. ADR: 원석 선정을 결정론적 규칙 엔진으로 한정하고 LLM은 카피 생성만 담당하는 아키텍처 분리
2. ADR: 세션/공유/초대 인증을 쿠키 대신 Bearer 토큰 + 해시 저장 방식으로 설계
3. ADR: 자유 입력 원문을 DB에 저장하지 않는 정책
4. ADR: 오행/관계 정보를 별도 엔터티(`FiveElementProfile`)로 분리해 `Recommendation`과 (Phase 3의) `RelationshipAnalysis` 양쪽에서 참조하는 데이터 모델
5. ADR: 패키지 매니저 선택(npm 유지 vs pnpm 전환)
6. ADR: 오행 계산에 명리학 전문 계산 엔진 대신 범용 중국 농력 라이브러리(`lunar-javascript`)와 단순 휴리스틱을 채택한 결정과 그 한계
7. ADR: 계정/인증 없이 비회원 세션만으로 민감정보(생년월일시) 처리 기능(오행 분석)을 제공하기로 한 결정과 위험 완화책(암호화, 세션 만료, 자기결정 삭제 경로)
8. ADR: 계정 기능(FR-FIVE-005)을 영구적으로 만들지 않고 보관함을 브라우저 로컬 저장소 기반 세션으로 구현하기로 한 결정 — 기기 간 동기화 불가, `localStorage` 접근 시 세션 토큰이 상대적으로 오래 노출되는 트레이드오프를 감수함(완화책: `/privacy`를 통한 언제든 삭제)

## Assumptions

- 담당 역할은 실제 조직 구조가 없어 "~확인 필요" 형태의 역할명으로 표기했다. 실제 담당자 배정은 팀 구성 후 갱신이 필요하다.
- 목표 결정일은 구체 일정이 없어 트리거 조건("Phase 2 착수 시점" 등)으로 표기했다.

## 추가 검증 필요

이 문서의 "미해결 질문" 표 전체가 추가 검증 필요 항목이다. 본 절은 향후 결정이 확정될 때마다 "확정된 제품 결정" 표로 이동시켜 갱신한다.
