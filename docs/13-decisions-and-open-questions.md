| **반복 추천 패널티(`repeatPenalty`)를 모든 컨텍스트(기본 추천 포함)에서 완전히 제거했다.** 추천 엔진은 이제 `recentStoneIds` 입력을 받지 않으며, 동일한 소원/감정/오행/관계목표 입력은 세션의 다른 추천 이력과 무관하게 항상 동일한 원석을 반환한다 | 사용자가 "오행 분석 결과에서는 자수정인데 관계 원석에서는 오팔이 나온다", 이어서 "오행 분석만 반복해도 원석이 계속 바뀐다"고 신고. 원인은 반복 패널티가 컨텍스트 구분 없이 세션의 모든 추천 이력(기본 추천 포함)을 함께 집계해, 오행 분석·관계 원석처럼 안정적이어야 할 결과까지 무관한 최근 활동에 따라 흔들리게 만든 것. 처음에는 오행/관계 컨텍스트에만 패널티를 제외하는 방안을 제안했으나, 사용자가 "기본 추천도 같은 게 나오는 게 맞다"고 명시적으로 판단해 전면 제거로 확정 | 오행 분석·관계 원석 컨텍스트에서만 패널티 제외, 기본 추천에는 유지(제안했으나 사용자가 기본 추천의 다양성 목적보다 예측 가능성을 우선하기로 판단해 미채택), `recentStoneIds`를 컨텍스트별로 분리 집계(미채택 — 이번 요청 범위에서는 과도하며 사용자가 애초에 반복 패널티 자체를 원치 않음) |
| **"나의 원석"(개인 오행 진단, `five-elements` 컨텍스트)을 소원/감정과 섞지 않고 오행 친화도 100%로만 정하도록 바꿨다**(`partner-five-elements`와 동일 가중치) | 사용자가 "오행분석 하면 자수정인데 관계원석에서 다시 하면 오팔이 나온다", "오행분석만 반복해도 원석이 계속 바뀐다"고 신고. 원인 중 하나는 개인 오행 진단이 소원(0.35)+보조소원(0.1)+감정(0.2)+오행(0.35)을 섞은 점수였다는 것 — 같은 생년월일이라도 그날 고른 소원/감정에 따라 결과가 달라졌다. "생년월일에서 나온 진단"이라는 이 기능의 전제와 맞지 않아 오행 100%로 변경 | 기존 가중치 유지(미채택 — 사주 기반 진단이 무관한 소원 선택에 흔들리는 문제가 남음) |
| **같은 오행을 가진 원석이 여럿일 때(예: 금(金) 원석 4개) 최종 1개를 정하는 동점 처리는 slug 알파벳순 그대로 유지한다.** 보조 오행(두 번째로 필요한 원소)을 추가로 반영하는 방안을 시도했으나 채택하지 않았다 | 원석은 오행 속성을 하나만 가지므로(`Stone.element`), 같은 오행을 가진 원석들은 "보조 오행 친화도"를 계산해도 전부 동일한 값이 나와 실제로는 동점을 전혀 깨지 못한다는 것을 구현 중 확인했다. 대안으로 "생년월일에서 나온 오행 비율 전체를 결정론적 인덱스로 써서 동점을 깨는" 방법도 제시했으나, 사용자가 "그것도 명리학적 근거가 없는 임의의 숫자 아니냐"고 되물었고, 두 방식 모두 근거 없는 휴리스틱이라는 점에 동의한 뒤 "그대로 유지(알파벳순)"를 선택 | 보조 오행 반영(구현 후 수학적으로 무효함을 확인해 되돌림), 생년월일 기반 결정론적 인덱스로 동점 분산(제안했으나 사용자가 "이것도 근거 없는 임의 숫자"라고 판단해 미채택) |
| **메인 화면을 "내 염원"/"내 사주"/"관계의 사주" 3가지 추천 방식 버튼으로 분기했다.** 소원+감정 기반 "기본 추천"(S02~S05) 자체와 API는 그대로 두되, 메인 화면에 별도 버튼으로 직접 노출하지 않는다 | 사용자가 명시적으로 요청("메인 화면에서 원석 추천 방식을 3가지 버튼으로 분기"). "기존 사주 추천 기능을 새로 만들지 말고 그대로 재사용, 메인에서 분기만" 원칙에 따라 기존 오행(S06)/관계(S09) 화면과 API를 그대로 재사용했다 | 기존 단일 CTA 유지 + 내부에 3가지 옵션 노출(미채택 — 사용자가 명시적으로 메인 화면 자체의 3분기 버튼을 요청) |
| "내 사주"/"관계의 사주" 버튼은 소원·감정 선택 화면(S02, S03)을 건너뛰고 곧바로 생년월일 입력으로 이동한다. 내부적으로 기존 `POST /recommendations/basic`을 기본값 소원/감정으로 조용히 1회 호출해 추천 ID를 만든 뒤 리다이렉트한다 | 오행/관계 화면이 기존에 이미 존재하는 `Recommendation` id를 URL에 요구하는 구조라, "소원/감정 없이 바로 생년월일 입력"을 만족하려면 그 id를 어디선가 만들어야 했다. 기존 API를 전혀 바꾸지 않는 방법(제안 A: 기본값으로 조용히 생성)과 기존 흐름을 그대로 앞세우는 방법(제안 B: 소원/감정부터 거치게 함) 중, 사용자가 "사주 기반으로만 판단하도록 해달라"고 답해 제안 A로 확정했다 — "나의 원석" 계산 자체는 이미 오행 100%(위 결정 참조)라 기본값 소원 선택이 결과(원석)에 영향을 주지 않는다 | 제안 B: 소원/감정 선택부터 거치게 함(미채택 — 버튼 이름("내 사주로 추천받기")과 실제 동작이 어긋남) |
| "내 염원으로 추천받기"는 생년월일을 받지 않으므로, 오행×목적 매핑 표의 목/화/토/금/수 5칸을 구분하지 않고 목적 그룹 하나에 속한 모든 원석을 합쳐(union) 후보로 쓴다 | 사주 입력이 없어 5개 오행 중 어느 칸을 써야 할지 판단할 근거가 없다. 대안이 마땅치 않아 이 방식으로 진행(사용자 확인) | 오행별로 나눠서 보여줌(미채택 — 근거로 삼을 사주 정보가 이 흐름에는 없음) |
| "내 염원" 매핑 표에 있던 원석 중 실제 23종 카탈로그에 없는 것(말라카이트, 문스톤, 호안석류, 침수정류, 옵시디언 등 20여 종)은 대체하지 않고 후보에서 제외한다. 그 결과 "학업" 목적 그룹은 후보가 라피스라줄리 1개뿐인 등 그룹별로 후보 수가 들쭉날쭉하다 | 매핑 표 대부분이 현재 카탈로그에 없는 원석을 참조하고 있어, "근거 없이 새 원석을 추가하지 않는다"는 원칙을 지키면 자연히 후보가 줄어든다. 카탈로그를 새로 확장하는 대안도 제시했으나 사용자가 "있는 것만 사용, 나머지는 빈 배열"을 선택 | 카탈로그 확장(원석 20여 종의 이미지·설명·fallback 카피를 새로 준비해야 하는 큰 작업이라 미채택), 비슷한 색상/의미의 기존 원석으로 임의 대체(미채택 — 근거 없는 대체 금지 원칙과 정면으로 충돌) |

## 대안 검토 메모

- **하단 탭바 vs 선형 단계형 내비게이션**: 짧고 목표지향적인 흐름 특성상 선형 진행을 채택했으나, 사용성 테스트 전까지는 가설이다([02-information-architecture.md](02-information-architecture.md#모바일-내비게이션)).
- **세션 토큰/공유 토큰 인증 방식**: 쿠키 기반 대신 `Authorization: Bearer` 헤더 방식을 채택해 CSRF 위험을 구조적으로 낮췄다([07-api-specification.md](07-api-specification.md), [12-privacy-security-compliance.md](12-privacy-security-compliance.md)).

## 위험

- 명리학/오행 계산의 정확도가 낮으면 서비스 신뢰도에 직접적 타격을 준다 → 사용자 승인 하에 "단순화된 초안"으로 Phase 2를 구현했으며, 프로덕션 공개 전 명리학 자문 검수를 강력히 권장한다([08-recommendation-engine.md](08-recommendation-engine.md), [11-implementation-roadmap.md](11-implementation-roadmap.md#실제-구현-참고-phase-2-오행분석-공유) 참조).
- envelope encryption의 KEK가 환경변수(로컬 `.env.local`)에만 존재하며 실제 KMS로 이전되지 않았다 → 프로덕션 배포 전 반드시 KMS 연동으로 전환해야 한다.
- 위기 표현 감지 정확도가 낮으면(과소 감지) 사용자 안전에, (과다 감지) 사용자 경험에 각각 악영향을 준다 → fail-safe(과다 감지 방향으로 보수적 설계) 원칙을 유지한다([09-ai-prompts-and-safety.md](09-ai-prompts-and-safety.md)).
- LLM 국외 이전 관련 법적 요건 미검토 시 컴플라이언스 리스크가 있다 → Phase 1 LLM 연동 전 법무 검토를 선행 권장한다.
- ~~비회원 세션의 민감정보(생년월일시) 삭제 경로 부재~~ → `DELETE /sessions/current`와 만료 세션 정리(즉시 정리 + 배치 스크립트)로 해결했다([07-api-specification.md](07-api-specification.md#delete-sessionscurrent), [11-implementation-roadmap.md](11-implementation-roadmap.md#실제-구현-참고-phase-2-삭제-경로) 참조). 남은 위험은 배치 스크립트를 실제 스케줄러에 연결하는 인프라 작업뿐이다.

## ADR 후보

다음 항목들은 정식 ADR(Architecture Decision Record)로 문서화할 가치가 있는 결정으로, 실제 구현 착수 시점에 별도 ADR 작성을 권장한다.

1. ADR: 원석 선정을 결정론적 규칙 엔진으로 한정하고 LLM은 카피 생성만 담당하는 아키텍처 분리
2. ADR: 세션/공유/초대 인증을 쿠키 대신 Bearer 토큰 + 해시 저장 방식으로 설계
3. ADR: 자유 입력 원문을 DB에 저장하지 않는 정책
4. ADR: 오행/관계 정보를 별도 엔터티(`FiveElementProfile`)로 분리해 `Recommendation`과 (Phase 3의) `RelationshipAnalysis` 양쪽에서 참조하는 데이터 모델
5. ADR: 패키지 매니저 선택(npm 유지 vs pnpm 전환)
6. ADR: 오행 계산에 명리학 전문 계산 엔진 대신 범용 중국 농력 라이브러리(`lunar-javascript`)와 단순 휴리스틱을 채택한 결정과 그 한계
7. ADR: 계정/인증 없이 비회원 세션만으로 민감정보(생년월일시) 처리 기능(오행 분석)을 제공하기로 한 결정과 위험 완화책(암호화, 세션 만료, 자기결정 삭제 경로)
8. ADR: 계정 기능(FR-FIVE-005)을 영구적으로 만들지 않고 보관함을 브라우저 로컬 저장소 기반 세션으로 구현하기로 한 결정 — 기기 간 동기화 불가, `localStorage` 접근 시 세션 토큰이 상대적으로 오래 노출되는 트레이드오프를 감수함(완화책: `/privacy`를 통한 언제든 삭제)

## Assumptions

- 담당 역할은 실제 조직 구조가 없어 "~확인 필요" 형태의 역할명으로 표기했다. 실제 담당자 배정은 팀 구성 후 갱신이 필요하다.
- 목표 결정일은 구체 일정이 없어 트리거 조건("Phase 2 착수 시점" 등)으로 표기했다.
